## Repository-specific records

### D09 — Mochi UI: tactile clay with one coherent behavior system

**Use when:** When building Mochi components, clay/SDF experiments, spring migration, haptic/audio behavior, or Figma token export.

[Recovered intent] Mochi begins with pastel clay, volumetric shadows, bento compartments, compression → overshoot → settle, and synchronized sensory feedback. Its enhanced handoff expands toward SDF clay, soft-body appearance, spatial sound, semantic/context/spatial/temporal/sonic tokens, guided journeys, and progressive disclosure.

[Observed implementation] The tree includes Astro/React components, enhanced shaders/audio, token files, and a separate framework-neutral spring engine. The engine provides explicit numeric configuration and stepping. Its acceptance contract requires parity, long-frame handling, overshoot, settlement, cancellation, cleanup, SSR, reduced motion, and an approved migration map.

[Concrete immaturity] The inspected ClayButton uses an independent bounce/duration-to-spring formula; hardcodes color/size values; schedules settle with an unmanaged timeout; renders no native disabled attribute; and uses pointer handlers for its clay state. These observations concern this sampled component, not every Mochi primitive. A global wrapper may affect motion, but local reduced-motion/cancellation behavior needs proof.

[Repair resolution — proposed] Give button semantics, keyboard/pointer activation, cancellation, focus, loading, disabled, and completion one state contract. Use a native button with the intended type/disabled semantics. Resolve preset units/migration instead of maintaining two conflicting physics authorities. Add provider-controlled haptic/audio opt-in and lifecycle cleanup.

[Reimagined horizon] A reusable tactile behavior and material library with a playful instrument/demo surface. Astro is the documented shell; WebGL enhances selected clay specimens without becoming necessary for ordinary controls.

[Carry-forward test] One button, slider, toggle, and modal are equally usable by keyboard/touch, honor disabled state, stop after disposal/cancel, and preserve completion under reduced motion. Numeric spring tests and perceptual material review are complementary.

## Practical continuation contract

1. Re-read current repository instructions and source before implementation. The baseline above identifies this publication, not a permanent execution HEAD.
2. Retain the full design horizon separately from the current demonstrator. Name what the demonstrator preserves, approximates, defers, or cannot prove.
3. Map tokens and controls to actual consumers with explicit units, ownership, accessible alternatives, and observable effect.
4. Complete the relevant interaction/error/cancellation states before promoting a reusable component.
5. Pair source/runtime checks with human correspondence review against the actual visual inspiration.
6. Keep proposed repairs unexecuted until a later implementation records its own revision, checks, and evidence.

## Scoped repair specifications

All are proposed and unexecuted. Static findings refer to the sampled files in the recovery source index; refresh them before making a code change.

| --- | --- | --- | --- |
| R01 | Button exposes no native disabled attribute; clay state handlers are pointer-specific. | Add deliberate type/disabled semantics and keyboard-equivalent state; retain focus and loading. | Disabled activation cannot fire; keyboard and pointer have equivalent completion. |
| R02 | Component maps bounce/duration separately from independent engine; settle timeout has no local cleanup. | Approve migration mapping; own scheduled work; respect cancel/dispose/reduced motion. | Parity fixtures, interruption and disposal checks; no late settle callbacks. |
